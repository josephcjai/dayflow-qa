## Finding 05 — confirmed fixed

**Dev's fix**, in `server/src/routes/authRoutes.ts`:
```ts
const passwordHash = user.password_hash || user.passwordHash;
if (!passwordHash) {
  return res.status(401).json({ error: 'This account was created with Google Sign-In. Please continue with Google.' });
}

const isMatch = await bcrypt.compare(password, passwordHash);
```

This is a minimal, direct fix — it guards exactly the condition the original finding
identified (`bcrypt.compare(password, null)` throwing rather than resolving `false`) and
returns a clean `401` with an actionable message instead of falling through to the route's
generic `catch` and a raw `500`.

**How this was verified — same limitation as the original finding, stated plainly again:**
this fix could not be live-reproduced against a real Google-linked account, for the identical
reason Finding 05 itself couldn't be: this suite has no way to self-provision a Google-linked
test user through the public API (creating one requires a real Google consent flow — see
`api/11-google-auth.spec.ts`'s header for the full reasoning). Confidence is high anyway:
- **Source diff confirmed** the guard is in place, checks the exact field (`passwordHash`)
  that was previously passed unguarded to `bcrypt.compare`, and sits before that call — not
  after, and not only on one of the two code paths (`password_hash` DB field / `passwordHash`
  in-memory fallback are both covered by the single `||` expression it guards).
- **Regression-checked**: the regular login path (right email/password, wrong password,
  non-existent email) still behaves identically — `api/01-auth.spec.ts` and
  `e2e/login-gate.spec.ts` both pass unchanged, so the new guard didn't disturb the common case.
- Dev's own reply independently reproduced the original `500` in their dev environment before
  fixing it (`{ "error": "Illegal arguments: string, undefined" }` — the same throw, same
  message shape as our isolated bcryptjs test predicted, just `undefined` rather than `null`
  depending on which of the two `||` operands was live) and reported all four login-path cases
  passing after the fix, which lines up exactly with what source review here would predict.

`api/11-google-auth.spec.ts`'s header comment has been updated to record the fix.

**Status: resolved**, pending an eventual black-box confirmation if this suite ever gains a way
to provision a Google-linked test account (not expected to change — see the file header).

## Method

Same isolated `dayflow-qa` stack as prior reports, rebuilt fresh from `967a679`.

Commit analyzed:
```
967a679 fix(auth): guard login against missing password_hash for Google-only users and update API docs
```
Diff: `server/src/routes/authRoutes.ts` (+7/-1), `docs/API_DOCUMENTATION.md` (+66/-12 net).

One thing worth recording plainly: the first full `test:e2e` run after this pin came back
19/21 failed, every failure timing out on `#app` never appearing after registration. This was
**not** a DayFlow regression — it was this suite's own known gotcha (documented in `README.md`):
`test:api` had just run immediately before, and its `api/13-proxy.spec.ts` deliberately exhausts
the shared auth rate-limiter bucket as its whole point. Every e2e test that registers a fresh
user through the UI hit the same exhausted bucket through nginx. Running `npm run
stack:reset-api` (restarts only the API container, no data lost) before the next `test:e2e`
attempt produced a clean 21/21, confirmed twice more after. Recorded here in full rather than
quietly re-run and not mentioned, consistent with this repo's practice of reporting what actually
happened.
