## Finding 02 — worth a closer look, because the first re-check was misleading

Re-running the *original* `07-proxy.spec.ts` test unmodified still failed after the fix. Before
assuming the fix was incomplete, we checked why — and it wasn't the fix, it was the test.

The original test tried to simulate "two different clients" by calling the same function twice
from the same test process with no distinguishing signal at all. That was never capable of proving
anything, fix or no fix — there's no way to generate two genuinely different real IP addresses from
one machine. Confirmed by walking through what `trust proxy: 1` actually does: it trusts exactly
what nginx itself directly observed as the connecting peer, and correctly **ignores** any
`X-Forwarded-For` value a client tries to inject further back in the chain. We proved this
directly:

```
$ # exhausted the limit as one (unspoofed) client, then:
$ curl -X POST .../api/auth/login -H "X-Forwarded-For: 203.0.113.99" ...
{"error":"Too many authentication attempts. Please try again after 15 minutes."}
HTTP 429   ← correctly still limited — the app doesn't trust a self-declared IP two hops back
```

That's the *correct, secure* behavior — trusting a client-supplied header that far back would let
anyone bypass the limiter just by lying about their own address. The test has been rewritten to
assert exactly that (spoofing `X-Forwarded-For` must not evade the limit) instead of the
unprovable "two different clients" scenario. New version passes; old version was asserting
something no single-machine test could ever confirm either way.

## Finding 03 — verified as a real restart, not just a passing test

The original `06-restart-persistence.spec.ts` had a workaround baked in: it restarted `api-qa`
itself right after `postgres-qa`, specifically because the crash bug meant the API wouldn't
survive on its own. That workaround has been removed now that the fix is confirmed — the test
restarts only `postgres-qa`, and the API is expected to reconnect by itself:

```
$ docker restart dayflow-qa-postgres && sleep 5
$ docker ps --filter name=dayflow-qa-api
dayflow-qa-api   Up About a minute        ← stayed up through the restart

$ curl -X POST .../api/auth/register ...
{"message":"Registration successful", ...}   ← and actually serving real DB-backed requests again
```

This also makes the test a live regression guard going forward — if the crash bug ever comes back,
this is the test that will catch it (the API would stop responding and the test would time out
waiting for it, since nothing restarts it for you anymore).

## Two test bugs this retest fixed along the way (ours, not DayFlow's)

Being upfront about these since they briefly looked like new product findings before we ran them
down:

1. **`07-proxy.spec.ts`'s original "second client" test could never pass** — covered above. Not a
   flake, not a regression; it was testing something impossible to test the way it was written.
2. **`e2e/time-lock.spec.ts`'s "future day" case failed on this specific retest run** because today
   (2026-08-31) happens to be a Monday — the test picked "tomorrow" as its future date, which lands
   in the *same* calendar week as today when today is a Monday, and a helper function picked the
   grid's Monday column regardless of which day was actually requested. Both bugs together meant
   the test was, by coincidence, checking today's own (already-past) 8 AM slot instead of a future
   one. Fixed to target dates a full week+ away and to select the actual matching day column, not
   just the first one in the grid.

Both fixes are in this repo now; full account in the commit history.
