## Finding 12 — verification

**The direct check:** the expected-failure marker QA added last round for this exact scenario now
reports *"Expected to fail, but passed"* — the designed signal that the bug is gone. It has been
converted to a normal test.

**Edge cases the new persistence/retry logic invites** (each run in a fresh browser context against
a notes endpoint stubbed to HTTP 500 and then unstubbed, checking what the server actually holds
after a fresh reload):

| Scenario | Result |
|---|---|
| Fail on day A → leave to B → recover → navigate | Day A saved ✓ (the original Finding 12 case) |
| Fail on day A → **reload during the outage** → recover → navigate | Day A saved ✓ — the failed-week set and the unsent text both survive the reload |
| Fail on day A → recover → **reload without navigating** | Day A saved ✓ — the launch-time auto-flush sends it |
| **Two** different weeks both failed → recover | Both saved ✓ — each retried against its own data |
| After recovery | Status pill "Saved" ✓; only 1 POST during recovery; **0 POSTs on 3 later pure-navigation clicks** ✓ (Finding 08 not re-broken) |
| Failed-week marker storage | Keyed per user (`dayflow_failed_notes_weeks_<userId>`) ✓ — one account's unsent edits aren't attributed to another |

A permanent test was added for the reload-during-outage case
(`e2e/notes-save-behavior.spec.ts`), since that is the half of the fix that is easiest to regress.

## Observations (not findings)

- **`v2.4.1` isn't tagged.** The reply lists `v2.4.1` as the target release, but the remote has no
  such tag; QA pinned the commit SHA. Worth cutting so the pin can go back to a name.
- **Edge not exercised:** if a failed week's stored data were ever missing from `scheduleData`,
  the retry loop skips it without clearing its marker, which would leave the pill on "Save failed"
  indefinitely. QA could not produce that state through the UI (stored data survived every reload
  tried), so it is noted only as a theoretical edge, not filed.
