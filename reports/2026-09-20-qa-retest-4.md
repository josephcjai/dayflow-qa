## Finding 12 (new) — a failed note save is dropped if you leave that day before the server recovers

**Severity:** Medium · `notes.js` `flushCurrentNoteEditor` / `state.js` failed-save marker

The failed-save marker (`STATE.notesSaveFailed`) records *which* week failed, but the retry flush
always saves the **current** week, and a successful save clears the marker regardless of week. Two
runs of the same scenario, server stubbed to 500 then recovered, POSTs logged:
```
E1 fail on A, STAY on A, recover, navigate away:
   POSTs after recovery = [week A (has the text)]   status "Saved"   Day A after reload = "ONLY FOR DAY A"   ✓
E2 fail on A, LEAVE to B while still failing, recover, navigate again:
   POSTs after recovery = [week A (has text, still failing), week B]   status "Saved"
   Day A after reload = ""                                                                          ✗
```
In E2 the next successful save (for week B) clears the marker, so week A's edit is never retried,
the pill reads "Saved", and the note is gone after a reload. Realistic trigger: a brief network
drop while editing, then moving to another day before connectivity returns.
**Suggestion:** key the failure marker per week (a set of failed week keys); on any flush, retry
*each* failed week's stored data, and clear only the entry whose own save succeeded.
Encoded as an expected-failure test in `e2e/notes-save-behavior.spec.ts` (flips loudly when fixed).
