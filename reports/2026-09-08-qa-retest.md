## Result: Finding 04 fixed

`PATCH /api/todos/:id`'s three-way branch now has a fourth, dedicated case for "neither field
provided" — an existence-only `SELECT`, not the old fallthrough into the completion-update branch:

```ts
} else if (completed !== undefined) {
  // update is_completed only
} else {
  // Neither field provided: no-op, but verify todo exists and belongs to user
  patchRes = await executeQuery(
    `SELECT id FROM todo_items WHERE id = $1 AND week_id IN (...)`,
    [id, userId]

```

Confirmed live: `api/08-todo-due-dates.spec.ts`'s regression case now passes — mark a todo
complete, `PATCH` with `{}`, re-fetch, still complete. Re-ran the full suite twice; stable both
times.

## One accuracy note on the dev team's write-up — not blocking

The response describes a second fix: *"the in-memory fallback did not touch `item.completed` when
`completed === undefined` while marking `updated = true`, introducing an inconsistency between
PostgreSQL and memory store state"* — and lists this as resolved. Checked directly against the
diff (`6fb7686..f0d3ebb`): the memory-store block in the same handler is byte-for-byte unchanged.
It still does:
```ts
if (item) {
  if (completed !== undefined) item.completed = !!completed;
  if (dueDate !== undefined) item.dueDate = dueDate;
  updated = true;  // ← still set unconditionally once a matching item is found
}
```
So that specific inconsistency (memory-store fallback marking `updated = true` on an empty PATCH,
without the new existence-style distinction the Postgres path now has) is still there. It's
low-stakes — the memory store is only reached when a Postgres query throws, which is the "database
is down" fallback path, not normal operation — and our test suite exercises real Postgres
throughout, so this didn't affect the 90/90 result. Flagging only for accuracy: the write-up's
Finding-04 root-cause description covers something the diff doesn't actually touch.

## While retesting: two things worth knowing, both ours, not DayFlow's

1. **A real e2e flake surfaced and was fixed.** A 3-run stress test of the full e2e suite showed
   an ~11% flake rate — a different test failing each time (`todo-due-date.spec.ts`'s Today/
   Tomorrow badge checks, then separately `todo-persistence.spec.ts`'s reload check), always the
   same failure shape: the todo was never created at all, meaning an Enter-key submission
   immediately after clicking a quick-action button occasionally raced the button's own UI update
   under load. None of DayFlow's frontend files changed in this fix commit, ruling it out as a
   regression from this release. Fixed two ways: added the missing settle-wait to the one test that
   didn't have it (a sibling test already did), and reduced Playwright's local worker count
   (4 → 2) with one local retry enabled — an honest acknowledgment that this machine's Docker +
   multi-Chromium load doesn't sustain full parallelism reliably, rather than chasing an
   unrealistic zero-retry standard. 3/3 clean runs after.
2. **Still no tag past `v2.3.0`**, now flagged a third time (see Phase 0 note in
   `docs/TECHNICAL_PLAN.md`) — not escalating, just noting the pattern.
