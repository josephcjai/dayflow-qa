`docker-compose.prod.yml` now reads:
```yaml
JWT_SECRET: ${JWT_SECRET:?JWT_SECRET must be set — see server/.env.example}
```
Verified directly, not just by reading the diff:
```
$ JWT_SECRET= docker compose -f docker-compose.prod.yml config

      JWT_SECRET: a-real-secret-value
```

Refuses to start without a secret, interpolates cleanly with one. **Status: resolved.**

## Finding 06 — narrowed, not closed

**What the fix actually did, confirmed by source diff:** `flushCurrentNoteEditor()` and
`flushNotesToApi()` are now genuinely `async` and `await ApiClient.saveNotes(...)` before
returning, with a "Saving..." → "Saved"/"Save failed" status transition tied to the real request.
Every navigation caller (`navigateDate`, the date-picker handler, the view-mode button handler,
`switchView`, `handleSwitchToDayView`) now `await`s the flush before changing
`STATE.selectedDate`/`currentWeekStart`. This closes the *specific* mechanism the original finding
described — a caller no longer proceeds to mutate state while its own flush call is still in
flight.

**Why it's not the full fix.** Re-running `e2e/daily-journal.spec.ts` after removing the waits it
used to need (on the theory that the fix made them unnecessary) came back green most of the time
but still failed intermittently — a different symptom shape than expected for a fully-closed race,
so this was investigated with a purpose-built diagnostic rather than assumed away. A small
standalone script logged every `/api/todos/notes` request and response with timestamps while
driving the exact day-switching sequence. It showed something the source diff alone didn't reveal:
**switching to Day view and opening the Notes tab — before typing anything — already fires two
independent, empty-content saves**, because the view-mode button handler, `switchView`, and the
date-picker handler each call their own `flushCurrentNoteEditor()`. Typing real content and
blurring fires a *third*, independent save. Awaiting inside any one of these calls only orders
that call's own request relative to itself; it does nothing to order it relative to a *different*
handler's already-in-flight request. Three-plus unsequenced saves firing within a second or two —
exactly what ordinary rapid navigation produces — can still resolve out of order, letting an
earlier (stale/empty) save complete *after* a later (real) one and silently overwrite it.

**Confirmed this is the same race, not a new one:** reproduced at roughly the same ~30% rate as
before the fix, across 10 repeated runs of the reload-persistence test. The fix reduced the
*likelihood* in the simplest single-navigation case; it did not eliminate the *cause*.

**Status: partially resolved.** `e2e/daily-journal.spec.ts` was restored to using explicit waits
between navigation steps — not because QA is comfortable with that as a long-term answer, but
because it's an honest reflection of what's actually reliable against the app as it stands today.

**Suggestion:** sequence writes for the same week/sheet — a simple per-key promise chain or mutex
wrapping `ApiClient.saveNotes` so a second call for the same key waits for the first's request to
actually land before firing its own, or a monotonic version/timestamp the server can use to reject
a stale write outright.

## Finding 08 (new) — the Finding 06 fix introduced a real performance regression

**Severity:** Medium · `src/js/notes.js`'s `flushCurrentNoteEditor`

`flushCurrentNoteEditor()` has no dirty-check — it unconditionally calls `ApiClient.saveNotes(...)`
every single time it runs, and per the fix above, it now runs **awaited (blocking)** before every
navigation action app-wide, not just ones that touch notes. A diagnostic script confirmed this
directly: clicking through Day/Month/Week view buttons and week navigation (`#nextWeekBtn`,
`#prevWeekBtn`, `#todayBtn`) **without ever opening the Notes tab** still fired exactly one `POST
/api/todos/notes` per click — 6 redundant saves for 6 clicks that never touched a note.

```
--- clicking view-mode buttons (never opening Notes tab) ---
[1] POST /api/todos/notes fired
[2] POST /api/todos/notes fired
[3] POST /api/todos/notes fired
[4] POST /api/todos/notes fired
[5] POST /api/todos/notes fired
[6] POST /api/todos/notes fired

TOTAL POST /api/todos/notes fired during 6 pure-navigation clicks (Notes tab never opened): 6
```

Before this round's fix, this was harmless — the call was fire-and-forget, so it never blocked
navigation even though it fired unnecessarily. Now every one of those navigation actions genuinely
waits on a network round trip that saves nothing new. This lines up with something observed
independently before this diagnostic even ran: this round's **entire** e2e suite got measurably
slower — not just the notes-related specs — with nothing else in the diff to explain it (batch1
went from ~16s to ~35–50s, batch2 from ~15s to ~50–60s, both runs otherwise unchanged). On a real
network (rather than this suite's local Docker loopback), this would be felt as a real added delay
on ordinary Day/Week/Month switching and week navigation, everywhere in the app, regardless of
whether notes are in use at all.

**Suggestion:** add a dirty flag — set when `setSheetContent`/the textarea's `input` handler
actually changes content, cleared on a successful save — and have `flushCurrentNoteEditor` return
immediately if nothing changed since the last save.
