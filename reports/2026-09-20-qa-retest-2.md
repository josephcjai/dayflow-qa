## Finding 06 — not resolved (and a correction to QA's earlier diagnosis)

**What is genuinely fixed:** write ordering. A request trace confirms each `POST /api/todos/notes`
response lands before the next one fires; the per-week queue does what the reply says.

**What is not:** with zero waits, the sequence "pick day → Day view → Notes tab → type → switch
day → type → switch back → reload" lost Day A's entry in **7 of 12** runs (higher than the ~30%
seen before — navigation is now faster because it no longer waits on no-op saves, so typing lands
earlier relative to the in-flight sync).

**Correction:** QA's previous report attributed this to unsequenced writes racing on the wire. The
new trace shows that was not the whole story. In the failing runs the notes POST for the week went
out **with empty content** (`hasA=false`) — the queue faithfully delivered an empty save:
```
[2017] --- typing A
[2029] GET   2026-09-28          <- late sync GET, issued after typing began
[2045] POST  week=2026-09-28 hasA=false hasB=false     <- saves the EMPTY copy
```
Clicking the Notes tab / Day view starts `syncWeekDataWithApi`, which awaits **three sequential
GETs** (slots, habits, todos+notes) and then runs `weekData.noteSheets = apiTodosNotes.noteSheets`
**unconditionally** (`state.js:257-259`) — no check for an unsaved local edit. If the user types
before that response lands, it replaces the typed text with the server's copy, and the next flush
saves that. This is a **read-clobbers-local-edit** race. The window is three round trips wide, so
on a real network (hundreds of ms per trip) it is *easier* to hit than on this local stack — e.g.
click Notes, start typing immediately.

**Suggestion:** in `syncWeekDataWithApi`, skip (or merge) the `noteSheets`/`notes` assignment when
`isNotesDirty` is true or the textarea differs from the sheet, and/or issue the three GETs
concurrently to shrink the window.

`e2e/daily-journal.spec.ts` still needs explicit waits to be deterministic; its header now
documents the corrected cause. It is not encoded as a `test.fail` — at ~58% it would itself flake.

## Finding 09 (new) — failed saves report "Saved" and are never retried

**Severity:** Medium · `notes.js` `flushCurrentNoteEditor` / `apiClient.js` `saveNotes`

`ApiClient.saveNotes` catches every fetch error and returns `false` (and returns `res.ok` for HTTP
errors) — it never throws. `flushCurrentNoteEditor` only handles a *throw*: its `catch` (which sets
"Save failed" and re-sets the dirty flag, per the reply) is unreachable for a failed request, and
it ignores the returned boolean. Verified live with the notes endpoint stubbed to HTTP 500:
```
D3  notes POST returns 500 -> status pill reads: "Saved"   (expected "Save failed")
D3b after server recovers, next navigation re-sent the unsaved edit: NO (0 POSTs)
```
The dirty flag is cleared *before* the request, so the edit is not retried either — the retry
behavior described in the reply does not happen. Net effect: an offline/500 save is silently
reported as success and dropped. **Suggestion:** use the return value —
`const ok = await ApiClient.saveNotes(...); if (!ok) { isNotesDirty = true; status = 'Save failed'; }`.
An expected-failure marker was added (`e2e/notes-save-behavior.spec.ts`) that flips loudly when
this is fixed.
